# 18 — Tracking

Tier: **CORE** (lifecycle tracking, notifications), **FUTURE** (email
integration, interview intelligence). Owning module: `tracking`.

## 1. Lifecycle Timeline

Every `Application` accumulates `ApplicationEvent` rows (doc 03/04) across
its full life: discovered → analyzed → matched → selected → prepared →
approved → started → submitted → confirmation → recruiter response →
interview → offer/rejected/withdrawn. `GET /tracking/timeline` (doc 05)
aggregates across all of a candidate's applications, ordered by
`occurred_at`, for the cross-application view; `GET
/applications/{id}/events` gives the single-application detail view used
by the Cockpit (doc 11 §6).

## 2. Manual Status Updates

`POST /applications/{id}/outcome` (doc 05) lets the user record an
`ApplicationOutcome` (`INTERVIEW|OFFER|REJECTED|WITHDRAWN|NO_RESPONSE`)
directly — this is the CORE path, since automated response detection
(§3) is FUTURE and optional. A manual update transitions
`Application.state` per doc 11 §3's `TRACKING → INTERVIEW/OFFER/REJECTED`
rules and writes a corresponding `ApplicationEvent`.

## 3. Email / Response Tracking — FUTURE

Optional, opt-in integration (not assumed available) that associates
inbound recruiter emails with an existing `Application` by
sender-domain/company-name/subject-line heuristics plus an LLM
classification pass, proposing an `ApplicationOutcome`
(`source=EMAIL_INTEGRATION`) that the user confirms before it's treated as
authoritative — never auto-applied without confirmation, since a
misclassified email could otherwise silently mark a live application
rejected. Architected as a bounded connector (reads a scoped mailbox
label/folder, never full inbox access) so it can be added without touching
`application`/`workflow` internals — it only ever writes through the same
outcome-recording path §2 uses.

## 4. Interview Intelligence — FUTURE

Once an `Application` reaches `INTERVIEW`, this subsystem (not built in
CORE/ADVANCED phases) would offer: company research summary (from doc 09
§2 enrichment), role-specific and resume-based likely questions, STAR-story
drafts grounded in candidate evidence (same evidence-validation discipline
as doc 12), mock interview sessions, feedback, and follow-up message
drafts. Data model placeholder: `ApplicationOutcome(outcomeType=INTERVIEW)`
is the anchor point this subsystem would attach to; no schema changes
needed to add it later.

## 5. Notifications

`Notification` rows generated by `tracking` on: high-match job discovered
(threshold-configurable), application needing attention (stuck in
`WAITING_FOR_APPROVAL`/`WAITING_FOR_USER` past a reminder interval),
manual application required, application submitted, application failed,
interview outcome recorded, deadline approaching (`Job.expiresAt`
approaching for a `SELECTED`-but-not-yet-`SUBMITTED` application),
important status change. Channels: `IN_APP` (CORE), `EMAIL`/`DESKTOP`
(ADVANCED), other channels (FUTURE). Channel preferences live in
`/settings/notifications` (doc 05).

## 6. Reminder Scheduling

A scheduled job (doc 33) scans for `Application` rows stuck in
approval/user-action states past a configurable threshold and emits a
reminder `Notification` — this is what makes doc 11 §7's "remains
indefinitely, never auto-approved" behavior still user-friendly rather than
a silent stall.

## 7. Failure Handling

| Failure | Behavior |
|---|---|
| Email classification (FUTURE) low-confidence | no outcome proposed; falls back to requiring manual entry |
| Notification delivery failure (email/desktop channel down) | in-app `Notification` row still created; delivery failure logged, retried per doc 30, never blocks the underlying state transition it's reporting on |

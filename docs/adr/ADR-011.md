# ADR-011 — Universal Form Abstraction

## Context
Application forms vary across hundreds of potential platforms; building
platform-specific handling for every one is unbounded engineering effort
and would leave any unadapted platform completely unsupported.

## Decision
A normalized `Form`/`FormSection`/`FormField`/`FieldType`/
`FieldConstraint`/`FieldAnswer` representation (doc 13 §2) that any page
can be interpreted into via DOM/accessibility/vision analysis, consumed
uniformly by the Browser Agent (doc 14) regardless of source platform.
Platform-specific adapters (doc 17 §4) are an optimization layered on top
for high-value, well-known platforms, not a requirement for basic support.

## Alternatives Considered
- **Adapter-per-platform as the primary mechanism, generic fallback as an
  afterthought**: rejected — inverts the actual value: the generic path is
  what gives the product broad coverage; adapters only improve reliability
  for a handful of high-traffic ATS platforms.

## Consequences
New, previously-unseen platforms are supported (at least at ASSISTED/
MANUAL fidelity) from day one without an adapter being written first.
Generic-path robustness (doc 13, doc 28) is therefore a first-class
engineering priority, not a secondary concern behind adapter development.

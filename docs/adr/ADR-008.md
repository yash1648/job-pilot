# ADR-008 — Explicit Application State Machine

## Context
An application's lifecycle spans many async steps (discovery, matching,
generation, execution, tracking) across potentially long time windows
(user approval can take days), with multiple valid entry/exit paths
(AUTO/ASSISTED/MANUAL, doc 11 §2) and failure modes (doc 30).

## Decision
A single, fully-enumerated `ApplicationState` enum (doc 03) with an
explicit, documented transition table (doc 11 §3), enforced as guards at
the service layer — no implicit state derived from other fields.

## Alternatives Considered
- **Implicit state (derive "where is this application" from a combination
  of nullable fields/timestamps)**: rejected — becomes unmaintainable and
  untestable as the number of fields grows, and makes the doc 11 §3
  transition table impossible to enforce mechanically.
- **A generic, configurable workflow-state library**: rejected as
  unnecessary abstraction for a state set that is well-understood and
  finite; doc 17's `Workflow`/`WorkflowStep` already handles the
  finer-grained execution-step sequencing where genuine flexibility is
  needed.

## Consequences
Every valid/invalid transition is testable directly (doc 26 §4). UI
(Cockpit, doc 11 §6) can render state unambiguously. Adding a new state
requires updating doc 03, doc 11 §3, and the guard code together —
doc 00's consistency requirement makes this an enforced discipline, not
an easily-missed step.

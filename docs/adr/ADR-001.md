# ADR-001 — Modular Monolith

## Context
The core domain (candidate → job → match → application) is a tightly
coupled decision chain still actively stabilizing. Microservices-from-day-
one would force distributed transactions or eventual consistency across a
chain where correctness (no duplicate applications, doc 03 §6) is a
user-facing requirement, not an eventually-resolved inconvenience.

## Decision
Single Spring Boot deployable, internally partitioned into modules with
enforced dependency rules (doc 02 §3, doc 34), sharing one PostgreSQL
database.

## Alternatives Considered
- **Microservices from day one**: rejected — premature service boundaries
  before the domain model (doc 03) has proven stable in production.
- **Unstructured monolith (no module boundaries)**: rejected — would
  accumulate the coupling microservices are meant to avoid, without any of
  the deployment simplicity benefits monoliths offer.

## Consequences
Simpler transactions, simpler local dev/test, single deploy unit. Requires
discipline (ArchUnit-enforced boundaries, doc 34 §3) to avoid the modules
degrading into a de facto unstructured monolith. Extraction candidates and
their triggers are documented (doc 32 §4) so the decision is revisited on
evidence, not never.

# ADR-007 — AI Provider Abstraction

## Context
ADR-005 chose Ollama initially, but the product must not be architecturally
locked to one provider — future needs (a hosted provider for specific
tasks, a different local model runtime) must be addable without touching
business-logic modules.

## Decision
All AI access goes through `AiService`/`EmbeddingService`/`VisionService`
interfaces (doc 06 §1) owned by the `ai` module; no other module imports a
provider SDK directly. Adding a provider means adding a new implementation
of these three interfaces plus a `ModelRouter` (doc 06 §2) configuration
entry.

## Alternatives Considered
- **Direct provider SDK calls from each consuming module**: rejected —
  would scatter provider-specific code across `candidate`, `jobs`,
  `application`, etc., making a future provider change or multi-provider
  routing a sweeping, error-prone refactor instead of a config change.

## Consequences
Slight indirection overhead for the sake of long-term flexibility.
Every AI call is uniformly observable (doc 29 §2 AI request metrics) and
uniformly subject to the Policy Engine's downstream validation (doc 16
§4) regardless of which provider actually served it.
